# Instructions for coding agents (Claude Code, Codex)

This repository holds the Google Apps Script that builds and maintains the
Household Finance Tracker, a Google Sheet that is both a usable household
finance workbook and the data store for a future web app. GitHub is the source
of truth for the code. Google Apps Script is only the place the code runs. The
owner pastes files into the Apps Script editor by hand.

The owner is not a developer. Write in a professional, plain tone without
jargon, and ask clarifying questions when something is unclear.

## 1. Privacy rules (never break these)

- This repository contains code and fictional data only.
- Never add real balances, income amounts, paychecks, debt balances, interest
  rates, credit scores, account numbers, transaction history, or statements.
  The owner enters those in the Sheet, never here.
- Never add real spreadsheet IDs, Drive IDs, deployment URLs, API tokens, or
  email addresses. Use placeholders and read real values at runtime (Script
  Properties, or the spreadsheet the script is bound to).
- The household members' first names (the Persons list in `Config.gs`) are
  part of the tracker's dropdowns and are allowed. Nothing else personal is.
- Sample data is fictional, generated by `SampleData.gs`, and every sample row
  carries `SAMPLE` in its Notes so it can be removed in one step.
- Never ask the owner for real statements, exports, or screenshots of real
  numbers to debug. Ask for a description, or reproduce the issue with the
  sample data.

## 2. Data-safety rules (never lose financial records)

- Financial rows are soft-deleted (`Is Deleted` + `Deleted At`), never removed.
  Every total already excludes soft-deleted rows; keep it that way.
- The destructive calls `clear`, `clearContent`, `clearContents`, `deleteRow`,
  `deleteRows`, `deleteColumn`, `deleteColumns`, `deleteSheet`, `setTrashed`,
  `removeFile`, `removeFolder` are blocked by `scripts/safety-check.sh` on
  every pull request unless the line carries `// SAFETY-APPROVED: <reason>`.
  They are approved in exactly two places:
  1. `buildWorkbook()` and the builders it calls, which run on a brand-new
     blank spreadsheet or after the owner confirms a full rebuild; and
  2. `clearSampleData()`, which removes only rows tagged `SAMPLE`.
- **Never run or recommend `buildWorkbook()` on a spreadsheet that holds real
  data.** Once the owner has entered real data, changes to an in-use workbook
  must be delivered as targeted upgrade functions that add or repair what is
  missing and leave entered rows alone. Setup-style functions must be safe to
  run more than once.
- Any function that changes many rows needs a dry-run or a confirmation that
  says what it will change before it changes it.
- Do not rename tabs, column headers, or named ranges unless asked. The
  Dashboard, Monthly Summary, the future app, and the owner's habits depend
  on them. List any such change in `CHANGELOG.md` and `docs/SCHEMA.md`.

## 3. Development rules

- Read `PROJECT.md`, `STATUS.md`, and `docs/BUILD_NOTES.md` before substantial
  work. `docs/HANDOFF.md` is the original specification; the "What not to
  change" list in its section 34 still applies.
- `apps-script/Config.gs` is the single source of truth for tab names, colors,
  dropdown lists, the category taxonomy, and every table's columns and
  formula templates. Change the schema there, never by hand in another file.
  Then run `node scripts/gen-schema.js` so `docs/SCHEMA.md` matches.
- Keep the financial model exactly as the handoff defines it: Income is
  authoritative for paychecks; Spending = Expense − Refund; Savings, Debt
  Payment, Transfer, and Split Parent rows are never spending; split children
  are; Dashboard cards follow the Selected Month while Current Flexible
  Spending follows today's week; months are first-of-month dates.
- Read the existing code and trace what calls a function before changing it.
  Prefer a targeted fix over a rewrite. Do not remove code that looks unused
  without finding out why it exists.
- After a meaningful change, update `CHANGELOG.md` with the date, what changed,
  the exact files to paste into Apps Script, anything to run, and what was
  tested where. Update `PROJECT.md` after architectural changes and
  `STATUS.md` after each work session.
- When the owner asks for a changed script, give the complete file, not a
  snippet.

## 4. Google Apps Script rules

- Code must run in the Apps Script V8 runtime. No Node-only APIs, no npm
  packages, no `import`/`require` in `.gs` or `.html` files.
- Each file in `apps-script/` is pasted into the editor as a file of the same
  name. All files share one global scope; keep top-level code to constants
  and function declarations so load order never matters.
- Keep calculations in pure functions that do not call Google services where
  practical, so they can be tested here with Node.
- Environment-specific values are never hard-coded. The script reads the
  spreadsheet it is bound to; the web-app token lives in Script Properties.
- Account for the 6-minute execution limit, authorization prompts, and the
  time zone (`America/Detroit`). The build runs well inside the limit; keep
  per-cell calls out of loops.
- Functions that should not be callable from a web app or the editor end
  with `_`.

## 5. Testing

- `node tests/run-tests.js` runs the whole build against the in-memory mock in
  `tests/mock-sheet.js` and checks structure, formulas, sample data, and
  every helper. Run it before every commit.
- The mock does not evaluate formulas. Formula correctness is checked in the
  Sheet by `runQA()` (Finance Tracker → Run QA checks), which re-computes the
  key totals in plain JavaScript and compares them with the formulas.
- Say clearly what was tested here and what still needs testing in Google.
  Never describe untested Google behavior as verified.

## 6. How code reaches the Sheet, and the handoff page

Code is deployed automatically: merging to `main` runs
`.github/workflows/deploy.yml`, which runs the tests and then pushes every
file in `apps-script/` into the Sheet's Apps Script project with `clasp`
(secrets `CLASPRC_JSON` and `CLASP_SCRIPT_ID` live in the repository's Actions
secrets, never in files). The owner no longer pastes files. If the deploy
fails, say so and fix it; never ask the owner to paste as a workaround unless
they choose to.

A change is still not finished until there is a step-by-step handoff page for
whatever the owner must do *in the Sheet* after the deploy: run
`upgradeWorkbook` after a schema change, set a Script Property, connect a
bank, check a result.

- Build it with `node scripts/build-handoff.js <spec.json> <out.html>` and
  publish the HTML with the Artifact tool. Keep the spec in `handoffs/`
  (for example `handoffs/<date>-<topic>.json`) so it is in the pull request.
- One step per card with a checkbox: which tab to open, which menu item to
  run, what to type where, and how to check the result. Use the `file` field
  only for a file the owner must paste by hand (rare now).
- Start with a named version in Version history as a restore point whenever
  the Sheet already holds data. Say what does not change.
- Give the owner the artifact link in the final message with a short summary
  of what the change does for them. Never make them assemble the steps from
  `CHANGELOG.md`.
- A schema change (anything in `TABLES` or `LISTS` in `Config.gs`) must be
  deliverable by `upgradeWorkbook()` on a live workbook: append columns, use
  `renamedFrom` for a renamed header, never remove or reorder.

## 7. Git workflow

- Never commit directly to `main`. Work on a branch and open a pull request.
- One pull request per change, with a plain-language summary and the list of
  files that changed in `apps-script/` (the deploy pushes them all).
- Merging (owner's standing instruction, 2026-11-10): the agent merges each
  pull request itself as soon as both checks (tests, safety) pass, without
  waiting to be asked, then watches the deploy and tells the owner what
  landed and what to run in the Sheet. Never merge with a failing check.
  Stacked pull requests merge in order (rebase the next one onto `main`
  after the one below it lands).
